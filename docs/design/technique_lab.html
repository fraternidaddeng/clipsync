01OKLab 渐变插值预计算色标

你整套配色的特征是低彩度、高明度、跨冷暖——这恰好是 sRGB 插值最容易翻车的组合。

你现在的底色渐变

sRGB中段浊化
OKLab明度守住

冷暖点缀对撞（差异最极端的情形）

sRGB穿过灰泥带
OKLab绕行，彩度不塌
为什么。 sRGB 逐通道线性插值走的是色彩空间里的直线，而两个色相之间的直线会从色域内部穿过——那里彩度必然低于两端，于是中段发灰发浊。OKLab 是感知均匀空间，同样的直线在感知上是「绕着走」的，明度和彩度都保持住。色相跨度越大、明度越接近，差别越明显——你的冷暖二色正好是这个最坏情况。

预计算色标表 —— 这是给双端用的

WPF 的 GradientStop 和 Compose 的 Brush.linearGradient 都只有 sRGB 插值。想在原生端拿到 OKLab 的观感，唯一办法是预先在 OKLab 里采样，把中间色标算出来，再喂给原生渐变。下面是实时算的，直接复制。

色标数7
色标数取奇数，保证中点被精确采样到——中点正是 sRGB 偏差最大的位置。7 个通常足够；两端色相跨度超过 120° 时用 9 个。再多是浪费，肉眼分不出来。

02超椭圆圆角Compose 现成 / WPF 自绘

左中右三种做法。拖滑块看 n 的影响：n=2 是正椭圆，n→∞ 趋近直角，n≈4–5 是「苹果那种」。
border-radius
圆弧接直线，在接点处曲率二阶不连续。放大看角落会觉得「鼓」。
corner-shape（新）
CSS 原生超椭圆。仅新版 Chromium，此格若与左格无异说明你的浏览器不支持。
参数化路径
自己算点。唯一能两端都精确一致的做法，下面给公式和生成的 path。
指数 n4.5

  
公式。 超椭圆 |x/a|ⁿ + |y/b|ⁿ = 1，参数式取点：

  x = a · sgn(cos t) · |cos t|^(2/n)　y = b · sgn(sin t) · |sin t|^(2/n)

  t 从 0 到 2π 采 64–128 个点，连成闭合路径即可。两端共享 n，各自选 a/b——Windows 收紧（对应 8–14px 观感），Android 放开（16–28px）。同一种角的性格，不同的尺度。

  
移植。 Compose 有 androidx.graphics.shapes.RoundedPolygon，可直接生成并转 Shape。WPF 没有现成物，要用 StreamGeometry 或 PathGeometry 自绘，把上面算出的点写进去——好在这是一次性工作，做成一个 SuperellipseBorder 自定义控件之后就一劳永逸。






  
03三层阴影的分解WPF 要套 Border

  
你那条 --glass-shell-shadow 其实是三个独立的物理现象。看清楚才知道怎么拆开移植。

  

    
① 外扩柔影
物体挡住环境光

    
② 1px 白环
边缘捕捉到的光

    
③ 内顶高光
上表面的镜面反射

    
三者叠加
薄瓷感

  

  
关键在于三者缺一不可，且顺序固定。 只有 ① 是「浮空的纸片」；加了 ② 才有厚度；再加 ③ 才是「半透明的材质」而不是「白色的面」。③ 那 1.5px 的内顶高光是整个通透感的来源——它模拟的是光线射入介质表层再反射出来，是玉、瓷、磨砂玻璃共有的特征。

  
WPF 的坑。 DropShadowEffect 一个元素只能挂一个，而且是位图特效、会强制光栅化、拖性能。正确做法是不用 Effect：
① 外扩柔影 → 外层 Border 挂唯一一个 DropShadowEffect，或直接用九宫格图片
② 白环 → 内层 Border 的 BorderBrush + BorderThickness=1
③ 内顶高光 → 再套一层 Border，Background 用一条从上到下 2px 高的 LinearGradientBrush
三层 Border 嵌套。Compose 侧简单些，Modifier.shadow().border().background() 链式叠即可。






  
04不重复的胶片颗粒承重墙

  
你现在用的是 200×200 的 turbulence。左边故意缩到 40px 让平铺暴露出来——大屏上你现在的版本会有同样的问题，只是周期更长。

  

    

    

  

  

    
40px 平铺 · 网格感明显

    
300px + stitchTiles · 接缝消失

  

  
三条修正。 一、viewBox 提到 300×300 以上，平铺周期越长越难察觉。二、必须带 stitchTiles='stitch'（你已经有了，保留）——它让 turbulence 在瓦片边界处连续。三、numOctaves 从 3 提到 4，颗粒的频率分布更接近真实胶片银盐，少一点「电视雪花」味。

  
移植最省事的一项。 别在原生端算 turbulence——直接把 SVG 渲染成一张 512×512 的 PNG 打进包里，两端平铺同一张图。这样不仅零成本，而且颗粒图案逐像素一致，是双端统一里最容易拿满分的地方。opacity 保持 .02，宁可偏弱。






  
05镜面流光承重墙

  
你 fluid_abstract_demo 想要的 "flowing light sheen"。本质就是一条斜的白色渐变在平移，不需要 WebGL。

  
剪剪相传

  
配方。 一条 linear-gradient(90deg, transparent, rgba(255,255,255,.85), transparent)，宽度约容器的 36%，rotate(18deg)，从 -40% 平移到 130%。关键是动画曲线用你的 cubic-bezier(.16,1,.3,1)，并且在 55% 处就走完、剩下 45% 留白——停顿比划过本身更重要，否则会像廉价的骨架屏加载动画。

  
移植。 两端都是平移一个渐变画刷，成本极低。WPF 用 LinearGradientBrush + TranslateTransform 动画；Compose 用 Brush.linearGradient 配 InfiniteTransition 驱动偏移。建议只在两个时刻触发：配对成功、以及首次连接建立。常驻会变噪音。

当下最流行的「通透」手法：模糊强度沿一个方向渐变。下面是真的（三层 backdrop-filter 各带一个遮罩渐变）。

  

    

    
底部渐进模糊 · 三层叠加

  

  
别对它动心。 它需要「多层 backdrop-filter + 各自的 mask 渐变」，而 WPF 连一层元素级 backdrop-filter 都没有。Compose 侧勉强能用 Modifier.blur + 渐变蒙版凑，但那是对自身内容模糊而非背景，观感完全不同，而且 MIUI 上还要掉一次。

可移植的替身：不做模糊，改做明度渐隐——底部压一条从透明到 rgba(255,255,255,.85) 的渐变。它给出的是「内容淡出边界」的同一种心理暗示，成本接近零，两端逐像素一致。在你的高调日光底色上，这个替身的效果其实差不太多——因为背景本来就浅，模糊和渐白的观感在浅底上是趋同的。这是深色方案做不到、而你选了浅色才白捡的便宜。
